## VT-03 — API authentication and account isolation: FAIL

The [Worker](https://github.com/begb0037admin/aimm/blob/codex/pluginhub-foundation/library-api/src/index.js), [Wrangler config](https://github.com/begb0037admin/aimm/blob/codex/pluginhub-foundation/library-api/wrangler.toml), [schema](https://github.com/begb0037admin/aimm/blob/codex/pluginhub-foundation/library-api/migrations/0001_foundation.sql) and [README](https://github.com/begb0037admin/aimm/blob/codex/pluginhub-foundation/library-api/README.md) were independently fetched. The code checks RS256/JWKS signature, issuer, audience, `exp`, `nbf`, a nonempty subject, guarded routes and account-scoped device queries. It rejects malformed device IDs, returns generic structured errors and `no-store` responses. These are source-level observations only.

Two concrete gaps require correction before account authentication can be relied on. First, when `aud` is an array, Worker lines 115–116 require `claims.azp === env.OIDC_AUDIENCE`. Auth0 documents `azp` as the **client ID**, whereas the audience names the API; this check can reject valid multi-audience access tokens. Second, lines 107–142 provision any valid token with a nonempty `sub` into an account, and lines 184–189 return `account_owner` unconditionally. Auth0 documents client-credentials tokens with machine subjects of the form `CLIENT_ID@clients`; there is no grant/client/scope or human-subject distinction. If such a client is authorized for the API audience, the code would assign it an account-owner identity. These are contract/security defects even though the Worker has not been deployed. See [Auth0 on `azp`](https://support.auth0.com/center/s/article/receive-the-client-id-claim-instead-of-the-azp-claim-in-an-auth0-access-token) and [Auth0 client-credentials example](https://support.auth0.com/center/s/article/value-of-the-audience-attribute-in-access-token-requests-and-its-significance).

The device-list and revoke queries use `account_id` predicates. Revocation uses two sequential updates rather than one transaction; partial application is possible if the second fails. Credential issuance and runtime cross-account tests do not exist. Wrangler has no route and the Cloudflare Workers search for `aimm-library-api-dev` returned no project; this limits exposure, not the source finding.

## VT-04 — Schema integrity and migration state: PARTIAL

The SQL gives accounts a unique `(oidc_issuer, oidc_subject)`, devices an account foreign key, and retention timestamps/indexes. But `device_credentials` and `action_receipts` each have separate `device_id -> devices` and `account_id -> accounts` references, with no composite constraint requiring the device and account to match. A row can therefore refer to a device owned by another account. Correct this before adding credential or action writes. `CREATE IF NOT EXISTS` makes repeated SQL execution tolerant of existing objects; it does not establish schema equivalence or migration history.

A read-only Cloudflare D1 Console query against the named development database (`66c91fd6-fae8-43a1-8e3b-372274acd7dc`) returned `_cf_KV` and the six application tables `accounts`, `action_receipts`, `device_credentials`, `devices`, `profile_comparisons`, `shares`. `d1_migrations` was absent. A separate read-only count query returned zero rows in all six application tables. This corroborates table presence and current empty application data, but does not prove complete DDL/index parity with the committed migration. [Cloudflare's migration documentation](https://developers.cloudflare.com/d1/reference/migrations/) says Wrangler tracks applied migrations in `d1_migrations`; Console execution was not registered. SQL/config refer to the same DB name and UUID. Reconcile actual `sqlite_master` DDL/indexes before registering or rerunning the migration.

## VT-05 — Retention, deletion and provider claims: PARTIAL

The decision record specifies 90 days from terminal state for action receipts; at most 30 days for shares/profiles; immediate active-data removal on confirmed account deletion; and backup expiry/purge within 30 days. The SQL has expiry fields, but the Worker and Wrangler config contain no scheduled cleanup, account-deletion endpoint, retention ceiling checks, or backup-purge control. The package acknowledges this. Do not put real user data in these tables before enforcement and deletion are evidenced.

The repository says Auth0 is selected, with no tenant or credentials established. The available sources and provider access did not establish actual Auth0 tenant state; this remains a reported account-state claim. Current [Auth0 pricing](https://auth0.com/pricing) and [Cloudflare D1 limits](https://developers.cloudflare.com/d1/platform/limits/) support the cited public Free-plan/limit descriptions, including D1 500 MB per DB and 5 GB total account storage. They are planning assumptions, not proof of tenant configuration, future pricing or zero actual spend. Provider account billing and legal-acceptance state were not independently inspected.
