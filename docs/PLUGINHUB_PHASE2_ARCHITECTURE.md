## Approved architecture direction

1. **AIMM-owned Mac companion** scans and acts on local plugins, keeps paths and secrets locally, and sends only permitted inventory metadata to the AIMM account. It initiates an outbound connection to the AIMM API for sync and action work. The UI does not need to call a localhost bridge.
2. **Authenticated AIMM account API** stores per-device inventory snapshots, check observations, account preferences and operation summaries. It separates private inventory, public shares and optional aggregate contribution. The current key relay and captures KV are not suitable as this authoritative store without new auth and data models.
3. **One site/ Hope inventory service** makes the page and Hope read the same account snapshot and observation timestamps. Hope actions use a named backend operation and return the companion's verified receipt. The existing `TOOL_DEFS`/`handleToolCall` routing is retained as the site-side entry point, with new plugin tools added when implemented.
4. **Explicit local action authorization** requires a fresh preview and confirmation for moves, Trash and uninstall operations. Hub launch and installer download are separate actions; a downloaded file or opened hub never counts as an installed update. The companion rescans after local changes.

The detailed contracts below are the approved design baseline. Partial non-production implementation and fixture evidence now exist; the full provider/runtime, isolation, recovery, browser, pairing, parity, and action gates remain open. See the latest handover and closeout for current verified status.

## Identity, pairing and permissions

1. A managed OpenID Connect issuer authenticates website users. The Library API validates issuer, audience, expiry and signature, maps the provider subject to an internal `account_id`, and issues an HttpOnly, Secure, same-site API session. Browser writes require a CSRF token. Every D1 query is scoped by `account_id`; the Origin allowlist remains an extra browser restriction, never the identity check. `api.aimixmasters.com` and `aimixmasters.com` are same-site; signed-in inventory on the GitHub Pages fallback redirects to the canonical domain.
2. On first run, the companion generates a device signing key locally and requests a pairing ID and a random polling secret over HTTPS. It opens a short-lived URL containing only the public pairing ID; the secret stays in companion process memory until completion, then is erased, and travels only in HTTPS polling request headers, never in a URL, log or browser. A short verification phrase derived from the pairing ID, server nonce and device public-key fingerprint appears in both the Mac window and browser approval page. The signed-in owner compares the phrases, sees the named Mac and approves once. The server enforces the account's device limit before approval, registers that exact public key, issues a device-scoped credential only to the polling Mac, and records the approval. The long-lived credential and private key are stored in Keychain. No manual code copying is required. Pairing is single-use, expires after 10 minutes, is rate-limited and is logged. The website can rename/revoke a device; revocation stops sync and action claims.
3. Device credentials are separate from browser sessions and scoped to that `device_id` and account. Rotate them, store only token hashes on the server, and deny a revoked device immediately. A companion never receives another device's commands or inventory. The Mac never receives the user's browser session cookie.
4. Version 1 has one `account_owner` browser principal per account and a limited public-share `viewer`; these roles are derived from the signed-in account or share token, not user-editable membership rows. The owner can change preferences, approve pairing, create shares and confirm actions; device writes follow the capability matrix below. A public viewer can read only the published share projection. Hope uses the current signed-in browser's API session through the shared `handleToolCall` executor. It cannot mint a device credential, unlock the exact-path preview or complete a local-action confirmation. A future ChatGPT Desktop/MCP client must use the same account API and scoped authorization, not a separate inventory copy.
5. The current AI relay's `/captures` remains independent. Its single-user KV and Origin-only gate do not grant access to the Library API. If AIMM later shares account auth across Workbench features, that is a separate migration with its own review.

**Device capability matrix:** the API authorizes each request against the paired credential's `device_id`, account, current entitlement and named capability. `inventory:write` permits only its own inventory chunks/finalize; `samples:write` permits only its own Samples chunks/finalize; `duplicates:write` permits only its own generation-bound analysis; `commands:read` permits only its own queue; `actions:write` permits prepared previews, events and signed receipts only for operations assigned to that device; `requirements:write` permits an owner-approved read-only project summary; `contributions:write` permits only disclosed fields while the current aggregate-consent record is active; `diagnostics:write` permits only redacted companion health, check errors and version. The server denies a route if that capability is absent or the path device ID differs. `GET /v1/diagnostics` is an owner read of those redacted records, not a device write. Revocation denies every capability immediately.

**Account provider gate:** before implementation, select an OIDC issuer with email/passkey or equivalent login, token rotation, account recovery, export/deletion, and a practical path to multiple customers. Cloudflare Access can protect a private Worker but is not assumed to be the eventual customer account system. The internal `account_id` must not be an email address so a provider migration does not rewrite inventory ownership.

Identity rules are versioned. Start with normalized vendor/product names plus reviewed alias tables and product/bundle IDs where reliable. Preserve the raw names, per-format versions and provenance locally. Never hard-code the earlier 873, 1,613 or 1,618 product totals; page and Hope both derive counts from one active generation and label the unit. Waves shell expansion, helpers and aliases need fixture-based verification before migration. A product has one visible card, with formats and files beneath it. The duplicate finder reports extra on-disk copies separately.

**Inventory publication:** the companion starts a generation, uploads bounded chunks with stable IDs, then finalizes after all chunks and counts are acknowledged. The API atomically switches the device's active generation only after validation; D1 transactional batch support is documented by Cloudflare. The companion retains its prior local generation until the server acknowledges finalization. Idempotent chunk keys permit retry without doubling rows. Deleting a device or account removes its projection under a documented retention policy. Any public share has its own copy and expiry.

All endpoints below use JSON over HTTPS, schema version `1`, request IDs, bounded page sizes and structured errors (`code`, `message`, `retryable`). The Library API rejects unsupported schema versions, invalid formats and cross-account IDs. A server operation status is never accepted as proof that a Mac file changed until the companion posts a verified receipt.

Version 1 action kinds are `scan`, `check_updates`, `reveal`, `open_vendor_hub`, `open_vendor_site`, `download_installer`, `open_installer`, `move_to_unused`, `offload`, `restore`, `trash_plugin_copy`, and `trash_old_installer`. `scan` and `check_updates` are read-only and need no WebAuthn; `reveal`, `open_vendor_hub` and `open_vendor_site` require an explicit user request but no WebAuthn. `download_installer`, `open_installer`, `move_to_unused`, `offload`, `restore`, `trash_plugin_copy` and `trash_old_installer` require the exact preview plus fresh WebAuthn confirmation; the API rejects their `confirm` call without a verified, unused assertion issued within the preview's 10-minute life. Batch work is an operation containing these item kinds, not an unbounded shell command. Each kind has a declared local capability and per-item receipt. `download_installer` is distinct from `open_installer`; neither is equivalent to a verified installed update. Duplicate removal is `trash_plugin_copy` only when the request item cites a current `duplicate_analysis` ID that the API verifies for the active generation, the owner sees the exact extra copy in the preview, and the Mac rechecks that a separate active copy still exists before Trash. A future kind needs a schema-version change and review before the companion executes it.

`GET /v1/library` includes active `generation_id`, `device_id`, `observed_at`, `last_attempt_partial`, product count, format count and rows; partial rows are never published. `GET /v1/checks` returns raw `update`, `up_to_date`, `manual`, `unchecked` or `error` outcomes plus last-good/stale indication. `GET /v1/status-summary` applies one versioned bucket function to those raw observations, paid flags, snoozes, marks and filters and returns counts plus its rule version and generation ID. The site and Hope display that returned summary; neither recomputes its own actionable counts. Every Hope answer names the selected Mac and observation time, and says when a Mac is offline or a check is stale.

## Operation state and local safety

```text
requested → preparing → preview_ready → awaiting_confirmation
                                           ↓ confirm before expiry
                                       queued → claimed → running
                                               ↘ completed / partial / failed
requested or queued → cancelled / expired
```

The site first requests an operation with an API-generated `operation_id`, random nonce, account/device identity, kind and selected opaque item IDs. The Mac resolves the live files and prepares a canonical versioned preview using RFC 8785 JSON canonicalization: account/device/operation/nonce, kind, product/format, active scan generation, each item's stable local ID, affected source/destination display paths, current version, symlink flag and permission result. For download/open actions it also binds AIMM adapter ID/version, artifact product/version/platform, Mac-derived official URL, allowed redirect hosts including the final host, size limit, expected digest or trusted signer, local destination and installed hub identity. The Mac derives vendor URLs from its own signed adapter table, never from a server command. If a direct artifact has neither an authenticated digest nor a verifiable trusted signer, the direct route is unavailable and AIMM offers only the vendor hub/site route. It computes SHA-256 over the canonical bytes, signs the digest with its Keychain-held device key, stores the full preview and digest in its SQLite journal, and posts the signed digest, redacted summary and a short-lived exact-path preview payload. The server verifies the registered device public key, re-canonicalizes the payload and checks its hash against the signed digest before accepting a matching pending request.

The exact-path payload is the signed canonical preview: account/device/operation/nonce, kind, product/format/generation, stable local item ID, source and destination display paths, current version, symlink flag and permission result. For an installer action it additionally includes AIMM adapter ID/version, artifact product/version/platform, Mac-derived official URL, allowed redirect/final hosts, maximum download size, vendor-published expected artifact digest or reviewed signing identity, local download destination and installed hub identity. The maximum size and expected artifact digest are route policy, not the installed plug-in's file size or binary hash. The payload excludes installed file size, installed binary hash, raw plist, folder grants and unrelated files. The Library API encrypts this payload at rest in a dedicated D1 preview table with a Worker secret, separate from the ordinary `operation` summary. Every read checks `expires_at = created_at + 10 minutes` and denies access at expiry even if the row remains. Confirmation/cancellation deletes the row immediately; a scheduled purge removes expired rows within one hour. The logical access lifetime is at most 10 minutes; physical encrypted-row retention can last up to one hour longer. `GET /v1/actions/{id}` returns redacted state only. The owner preview screen first shows that redacted state. A person explicitly chooses to inspect exact paths; `POST /v1/actions/{id}/owner-preview/unlock` requires a fresh WebAuthn assertion with `userVerification: required`, bound to account, operation ID, digest and expiry. It mints a one-use, two-minute capability kept only in the preview UI's memory. Only `GET /v1/actions/{id}/owner-preview` with that capability returns the decrypted paths. The Hope tool executor has neither the unlock flow nor the capability; an explicit tool allowlist excludes unlock, exact-path GET and confirm. The single-file site's implementation must create a private preview UI module/closure scope for the one-use capability, separate from the shared Hope executor; this is a build requirement, not a current-code claim. The API rejects a normal session/CSRF-only read. Paths never enter Hope context, generic action reads, analytics or logs. This is the narrow, short-lived exception to the [Phase 1 data boundary](PLUGINHUB_DATA_BOUNDARY.md).

The person reviews the exact preview before choosing Confirm. The API records an owner-confirmed authorization bound to the digest, generation and expiry. Confirmation requires the current owner session, CSRF token and a separate fresh WebAuthn assertion with `userVerification: required`; its challenge binds account, `operation_id`, digest and expiry. The API verifies the assertion and consumes it once. The browser confirmation UI invokes WebAuthn only after the person's explicit Confirm action; the Hope tool executor has no confirmation route or assertion. The command returned to the Mac includes that verified authorization and digest. Before execution, the Mac checks its own journaled digest and all bound fields against the returned command, fetches current authorization, checks expiry/revocation, then re-resolves every item. Any change of path identity, symlink, version, destination, permissions, generation or duplicate extra-copy classification invalidates the preview and requires a new one. Destructive commands expire 10 minutes after preview creation and cannot be revived after reconnect. Read-only `scan` and `check_updates` commands have a separate 24-hour expiry and never carry file-action authorization.

The companion journals each item before it acts. Same operation ID plus item ID is idempotent: transport replay resumes unfinished items and never repeats a completed move/removal. An explicit `POST /v1/actions/{id}/retry` accepts `{item_ids, idempotency_key}` and creates one child operation for parent receipt items in `failed`, `skipped` or `needs_permission` only. The server rejects completed, cancelled or unknown IDs, binds the child to the parent/device/account, and returns the same child on idempotent replay. The Mac resolves eligible items afresh; any file action receives a new digest, expiry, exact preview and user verification. A batch receipt contains per-item `completed`, `failed`, `skipped`, `cancelled` or `needs_permission`, with observed evidence and a rescan generation. The Mac signs the receipt; the API verifies its device binding. `partial` stays partial even when one item succeeds. The site polls the API while an operation is visible and shows an offline/unknown state if the companion stops reporting; it does not infer success from elapsed time.

For local file operations, the companion restricts paths in its own code to connected roots, checks symlinks and collisions, and uses recoverable Trash for uninstall. Move to Unused/offload records source and destination; a cross-volume copy is verified by content before the source is removed. Restore refuses occupied destinations. No generic `rm -rf` fallback or always-running privileged daemon is part of the design. If the OS requires elevated access, request it locally for the named item and record denial or partial completion. Direct installers remain in a local managed download folder; before download the Mac checks the bound URL/allowed final host, product/version/platform and size, then verifies the downloaded file's digest or trusted signature. `open_installer` rehashes or revalidates the same local file immediately before launch and refuses a changed artifact. Vendor hubs and vendor websites are separate routes. Launching an installer, completing a download, and verifying a new installed version are separate receipt states.

## Status, vendor routes and scheduling

The check engine uses AIMM-owned vendor adapters with declared evidence source (`public_vendor`, `local_hub`, `manual`) and cache TTL. Adapters run in the companion when local hub state is needed; public sources may be checked by an AIMM service if its terms and access permit. Each adapter emits source timestamp, installed/latest versions, paid-upgrade signal, confidence, URL route and explicit failure reason. Cached last-good data remains labelled stale after a failed refresh. Vendor-specific comparators can override a conservative generic version parser with documented fixtures. A verified direct installer route is permitted only for a current Mac artifact and the exact product/version; otherwise show hub or vendor page/manual check. The Phase 1 970 static candidate keys and 13 saved direct installer candidates are research leads, not AIMM support claims.

The companion scans standard AU/VST2/VST3/CLAP folders at first setup, on request and on a user-enabled schedule, adding custom roots only after the user selects them. A completed scan syncs automatically when paired and online. Update checks can run on daily/weekly/monthly preference with manual `check_updates` requests from the site; manual `scan` is a distinct command. On an offline Mac, the site keeps the last complete snapshot but displays age and connectivity; Hope cannot imply a check occurred. User marks, snoozes, hidden state and paid-upgrade preferences are applied by the API's shared bucket function over raw observations and retain revision history.

## Hope, Workbench and the existing Library

The current `allPlugins()` reference catalogue continues to serve music guidance and stage recommendations, but it must be clearly separated from verified installed ownership. The installed Library, Workbench owned-plugin picker and Hope's `list_installed_plugins`, `get_plugin_status`, `get_plugin_action_preview` and `get_action_result` tools all call the same authenticated Library API. Existing `list_plugins`/`get_library` calls must stop presenting reference entries as installed ownership; their descriptions and digest are migrated only when the new API is live. The shared `handleToolCall` executor remains the typed/voice integration point, preserving Hope's current voice/chat mechanics. Hope tool results may include canonical product/vendor names, formats, installed/latest version labels, status, selected device display name and observation time. A user may rename the Mac to a neutral display label before sharing; the default label may contain a personal name and is disclosed. `get_plugin_action_preview` returns only the redacted summary; exact paths appear solely in the owner preview UI. Hope results omit exact paths, project names/content, licence values, pairing data, tokens and raw diagnostic errors. The browser discloses the permitted tool result to its selected voice/LLM provider as part of a user request; this is explained in the Library privacy UI. Desktop Hope can later use a scoped MCP adapter to the same API; no additional catalogue or local file authority is created for it.

The Library UI retains the approved MixCheck-cohesive design: collapsible left navigation with distinct monochrome icons, coloured square pills with white text, three-column vendor cards where width permits, dense row layout without vertical holes, and Hope's persistent right rail. Status/tool/catalogue tabs are backed by the account API; a status cannot display an update badge without an observation. Vendor marks are sourced/licensed for AIMM and have a fallback icon.

## Shares, profiles, vault and diagnostic boundaries

List sharing and profile comparison are separate from routine account sync. Before creating a public list, the user previews selected vendors/fields and expiry; hostname and local paths are omitted by default. The API uses opaque share tokens, optional stronger passkey policy, rate limiting, revocation and deletion. Logic/Cubase project parsing happens on the Mac from a user-selected file; only an optional requirements summary is synced, never a DAW file. AAX/Pro Tools paths remain excluded. The licence-key vault uses Keychain with user-presence unlock and local encrypted export/import; the Library API and Hope never see key values. Optional aggregate contribution has a separate explicit opt-in and field disclosure. Diagnostics include app/API/check versions and redacted errors, excluding secrets, ordinary paths and installer files. AIMM entitlement checks are independent of users' vendor plug-in ownership.

## Build sequence and cutover gates

1. **Foundation:** select OIDC provider and build Library API account/device model in isolation; keep the existing key relay and live site unchanged. Create schema migrations and a non-production D1 database.
2. **Read-only companion:** build the signed-app skeleton, pairing, AU/VST2/VST3/CLAP scan and local journal; exclude AAX at the scanner source. Sync a complete generation. Confirm product/format counts from one generation and investigate aliases/utility bundles.
3. **Read-only site/Hope:** add an account-backed inventory behind a feature flag. Compare it with the present browser scan on this Mac. Preserve the current Library as fallback until parity is demonstrated. Make Hope read the same snapshot with age/device labels; preserve chat/voice routes.
4. **Status and preferences:** implement current vendor adapters, raw status/cache semantics and account preferences. Expose only verified update actions; complete the 31-row UI mapping.
5. **Local actions and tools:** implement preview/confirmation/receipt flow in increasing risk order: reveal and hub open, direct download, installer queue, move/restore, Trash uninstall, duplicate and old-installer cleanup, vault and sharing. Each action class has per-item failure and recovery checks.
6. **Cutover:** once AIMM-owned scanning and actions are verified without PluginHub, switch Library and Hope to the account API. Then separately stop/remove the PluginHub-dependent LaunchAgent and retire the uncommitted bridge candidate using a reviewed rollback plan. Do not remove PluginHub or local data merely because the new UI exists.
7. **Release:** independent Terminal review, parity walk, signed/notarized companion artifact, site/API verification, and Kevin's review of a concrete release candidate before merging/deploying.

The live browser scan is a migration comparator, not the canonical future store. Do not import PluginHub's database or private catalogue. Any user favorites/tags in AIMM are mapped to canonical IDs only after identity confidence is checked, with an export/rollback copy. The companion can be unpaired without deleting local plug-in files; account deletion has a separate metadata purge. App update rollback keeps the previous signed release and compatible local database migration.

## Design assumptions and remaining decisions

| Item | Current decision or open gate |
|---|---|
| Account identity provider | Protocol fixed to OIDC; select a concrete issuer before implementation. Current Worker has no account auth. |
| Companion packaging | Native Swift app is recommended; Xcode-capable signing/notarization environment is required later. The current Mac only has Command Line Tools active. |
| API persistence | D1 for authoritative metadata. Confirm schema size, migration and quota against the intended release tier before deployment; no new binding was created now. |
| Live action transport | Outbound bounded polling first, with explicit stale/offline UI. A real-time channel is an optimization if measured progress needs it. |
| Vendor update coverage | Rebuild adapters independently and validate vendor terms, current endpoints and Mac artifacts. A direct-download digest must come from authenticated vendor release metadata or an AIMM signed adapter manifest; alternatively verify a trusted Mac code-signing identity against a reviewed allowlist. No digest or trusted signer means hub/site only. The static PluginHub registry is not an AIMM support guarantee. |
| Samples view | P31 is in parity scope, but installed source did not expose its feature-flag default or full behavior. Review visible manual/app behavior before final UI contract. |
| Entitlements and commercial access | Data model and API gate are specified; pricing, trial length and device limit require a product decision before launch. |
| Operational retention | Before implementation is authorized, decide and document exact retention windows for action receipts, profiles, shares and deleted accounts. Treat the approved schedule as a foundation-phase entry gate and verify enforcement before production. Short-lived previews expire and are purged; local full journal remains on the Mac. |
